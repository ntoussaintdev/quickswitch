Runbook guideline

How to write an operator runbook: a page someone follows, step by step, to set up, deploy, change or repair a system. It builds on the HTML documentation guideline (page shell, contents, numbering, dark mode, tables) and the step naming guideline. Copy all three into a project's docs/tips/ together.

1. Summary

  • A runbook is an HTML page in docs/runbooks/, never Markdown, in the page shell of the HTML documentation guideline.
  • It opens with a summary, then "Before you start", then numbered sections of numbered, named steps, then verify, rollback and troubleshooting.
  • Step numbers run on across sections, so "step 14" is one place in the whole page.
  • Every command block has a where label that says where to run it: Local, On the VPS, In GitHub.
  • A section that must work before the next one ends with a gate: what to look at, and what it should show.
  • Secrets have their master copy in ~/Secrets/<project-stub>/, never in a repository. You fill in the local copy and push it to the server; you never edit only on the server.
  • Dev steps come first. Staging starts with the operator's deploy; live is a later stage.
  • Placeholders are in capitals (VPS_IP). No real secret value ever appears in a runbook.

2. What a runbook is

  • A runbook is followed: set up a server, deploy a release, rotate a key, restore a backup. Each step changes something or checks something.
  • A plan says what will be built and why. A guide explains how something works. If a page is mostly explanation, it isn't a runbook; link to it from the runbook instead.
  • One runbook per job. "Set up staging" and "Release to staging" are two runbooks when they are done at different times. A page that does both splits at a clear section with its own gate.
  • The runbook is for the operator. An AI agent writes and updates it, but deploys and server commands are run by the operator, who follows it.

3. Page layout

In this order. Sections are numbered (HTML documentation guideline §3) and named by what they achieve (step naming guideline §4).

  1. Title and purpose. An h1 naming the job ("Deploy to the VPS"), then one or two sentences: what this runbook gets done, for which environment, and how long it usually takes.
  2. Summary. Section 1. A few bullets: the shape of the procedure, and where the parts run. A long runbook adds an At a glance list of just the step names.
  3. Before you start. What must already be true and what is needed at hand: access (SSH key, dashboard logins), tools (Git Bash, gh), the ~/Secrets/<project-stub>/ folder and which files in it, and the runbooks that come first.
  4. The procedure. One numbered section per stage ("3. Put the files on the server"), each a numbered list of named steps, each stage ending with a gate when the next stage depends on it.
  5. Verify. How to tell the whole job worked, in checks anyone can run: a URL that answers, a command whose output shows the new version, a page that signs in.
  6. Roll back. How to undo the job, or say plainly that it can't be undone and what to do instead (database migrations usually can't be).
  7. Troubleshooting. A table: What you see | Likely cause and fix. One row per symptom someone actually hit or is likely to hit.
  8. Reference (optional). Tables of files, settings and common commands that the steps point to. Settings tables name each key, where its value comes from, and whether it is secret.

4. Steps

  • Numbered and named. Every step is an item of an ordered list, starting with its name in bold (step naming guideline): 14. Push the config files. Then the details.
  • Numbers run on. Each section's list continues from the last with <ol class="steps" start="14">, so a step number is unique on the page. When a step is added or removed, renumber the rest and fix every "step N" reference.
  • One job per step. If the name needs "and", it's probably two steps. A step may hold a short command block or a nested list of settings.
  • Commands are copyable. A command goes in a <pre><code> block under a where label (§5), complete and ready to paste, with placeholders in capitals (§9). Don't put prompts ($, #) in front of commands.
  • Say what success looks like. When the output matters, say what it should show ("prints ready"), not only what to type.
  • Safe to repeat. Prefer commands that do no harm when run twice (install -d, cp -n, mkdir -p). When a step can't be repeated, say so.

6. Gates and notes

6.1 Gates

  • A gate closes a stage the next stage depends on. It names one observable result: a page, a command's output, a dashboard row.
  • Write it as what to check and what it should show: Gate: site-files.sh prints ready.
  • Don't move on until it passes. If it can't pass, go to troubleshooting, not to the next stage.
Gate: the repository's Actions secrets list shows VPS_IP, VPS_USER, VPS_DEPLOY_KEY and VPS_KNOWN_HOSTS.

6.2 Notes and warnings

  • Note (.note): context the reader needs to do the step right, such as why a value differs per environment.
  • Warning (.note.warn): something that breaks production, loses data or leaks a secret if done wrong. Start with the rule in bold: Never set DEV_AUTH_BYPASS in production.
  • Use them sparingly. A page full of warnings has none.
.note      { margin: 16px 0; padding: 12px 14px; border: 1px solid var(--note-line); border-radius: 8px; background: var(--note); }
.note.warn { border-color: var(--warn-line); background: var(--warn); }
.note.gate { border-color: var(--good-line); background: var(--good); }

7. Secrets

7.1 The rule

  • Master copy in ~/Secrets/<project-stub>/. Every generated or filled-in secret (server env files, passwords, keys, tokens) has its master copy on the operator's computer, in one folder per project and environment: ~/Secrets/little-loves-staging/, ~/Secrets/little-loves-live/. Never in a repository, not even gitignored on the server.
  • Fill in locally, then push. A runbook starts each server file from its template in ~/Secrets/<project-stub>/, fills it in there, and pushes it to the server. A later change is made to the local copy and pushed again. Never tell the reader to edit a secret file only on the server: the next push undoes it, and the local copy goes stale.
  • Hosted variables are copies too. Values set in GitHub Actions secrets, Railway or another dashboard have their master copy in the same folder (for example ~/Secrets/paragon-api-live/railway.env). Rotating a value means: update the local copy, then the platform.
  • Write generated values straight to the local file. openssl rand -hex 32 output goes into the local env file, not into a terminal scrollback, chat or ticket.
  • Never print values. Check scripts print setting names that are missing or still placeholders, never values. A runbook never shows a real value, and never asks the reader to paste one into chat.
  • Exceptions, stated where they apply. SSH keys stay in ~/.ssh. A long-lived signing key may be kept offline only. Files a deploy writes itself (.deploy.env) aren't kept locally. A local-dev .env with dev-only values may stay gitignored in the repository folder. Say which exception applies in the step.

7.2 Folder names

<project>-<environment>, lowercase, with hyphens: little-loves-live, tossandtumble-staging, chartchemy-mini. Secrets for shared infrastructure (the VPS itself, the edge, a mail server) go in a folder named for it: ~/Secrets/vps-contabo/, ~/Secrets/mailcow/. The "Before you start" section names the folder the runbook uses.

7.3 The push step

One push block per runbook, which later steps refer to. It strips Windows line endings (Docker would keep the \r in every value), never leaves a secret file readable by others, and sets the final modes.

Local (Git Bash) 
cd ~/Secrets/PROJECT-ENV
for f in api.env web-config.json; do
  tr -d '\r' < "$f" | ssh deploy@VPS_IP "umask 077; cat > /opt/SITE_SLUG/$f"
done
ssh deploy@VPS_IP "cd /opt/SITE_SLUG && chmod 600 api.env && chmod 644 web-config.json"

After a push, the step names the container to restart so the new values are read.

Never put a secret in a file served to browsers. Public config (such as web-config.json) holds only publishable values. Say so next to the step that fills it in.

8. Environments

  • Dev, then staging, then live. In a runbook that covers more than one environment, the dev steps come first. Staging steps are a later stage that starts with the operator's deploy; live comes after that. Don't mix them in one pass.
  • Say which environment each step is for when the page covers more than one, in the section name ("5. Set up staging") or a table of per-environment values.
  • Separate values per environment. Each environment has its own secrets folder and its own generated values. Say "don't reuse live's" where a reader might copy one.
  • Live is touched last and least. A step that changes live data or live settings carries a warning and, where possible, a way back.

9. Placeholders and values

  • Placeholders are in capitals with underscores: VPS_IP, SITE_SLUG, YOUR_GITHUB_OWNER. Explain each one the first time it appears, or in "Before you start".
  • Use the real names of things that aren't secret: paths, user names, domains, schema names, setting keys.
  • Example values use reserved names: example.com, 203.0.113.10.
  • Never a real password, key, token or connection string, not even an old one.

11. Checklist

  1. Format. HTML in docs/runbooks/, in the HTML documentation guideline's shell: dark with a light toggle, side contents, numbered sections, sticky table headers.
  2. Layout. Summary, Before you start, procedure, Verify, Roll back, Troubleshooting, in that order.
  3. Steps. Every step numbered and named; numbers run on across sections; every "step N" reference is right.
  4. Where. Every command block has a where label.
  5. Gates. Every stage the next one depends on ends with a gate.
  6. Secrets. Master copies in ~/Secrets/<project-stub>/, filled in locally and pushed; no step edits a secret only on the server; no real value anywhere on the page.
  7. Environments. Dev before staging before live; per-environment values kept apart.
  8. Read the names. The step names alone tell the whole procedure (step naming guideline §6).
