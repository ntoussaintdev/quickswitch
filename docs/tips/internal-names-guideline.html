Internal names guideline

For every app with screens people use, and the documentation written for them · created 2026-11-25 · from Little Loves, where a plan reference (“plan n8”) and a field key (loyaltyGiftUnit) reached the back office

1. Summary

  • What people see in an app speaks their language: the words on the screen, the shop, the till, the customer. It never shows how the app is built or how it was planned.
  • Plan references, section numbers, tweak numbers, field keys, table and column names, raw status values, function names and file paths stay in code comments and internal documentation.
  • Values that come from the code (fields, statuses, origins, error reasons) reach the screen through one label map, never as the raw value.
  • A diagnostic view may show raw records, folded away under “Technical details”, for the people who diagnose problems only.
  • The user guide follows the same rule as the screens. Plans and runbooks may cite anything.

A name is not internal when it's what the reader sees and uses elsewhere: a program the reader installs and recognises (“the sidecar”, when that's what it's called on their PC), a setting's label in another app's screen, a file the reader is asked to open. The test: would the reader recognise the word without having seen the code or the plans?

3. Where the rule applies

Everything a user reads, whatever produces it:

  • Screens: headings, labels, column headers, select options, buttons, help text, empty states, banners, toasts, confirm dialogs, tooltips, placeholders.
  • Accessible text: aria-label, title, alt text. A screen reader user hears it.
  • Text the server sends to a screen: error messages, warnings, report and permission descriptions, summaries of changes, reasons in lists.
  • Emails, notifications, alerts, PDFs, exports (column headers, sheet names) and printed receipts.
  • The user guide, help pages, release notes for users, and in-app tours.

Not covered, and free to cite anything:

  • Code comments, commit messages, test names and test data.
  • Template comments the framework removes at build time (Angular strips HTML comments from templates by default). Check that yours does before relying on it: a comment shipped to the browser is visible in the page source.
  • Plans, runbooks, implementation logs, architecture notes and other internal documentation.
  • Server logs and log messages meant for whoever operates the app.

4. What to write instead

  1. Say what it means for the reader. Not “Until plan n8 the till names one bad item”, but “The till names one bad item each time, so a re-run may stop at the next one.” If a limit will go away later, say what happens now; the screen changes when the limit does.
  2. Use the word the screen already uses. If the product page labels a value “Points per item sold”, every other screen, message and email calls it that too.
  3. Turn codes into words. pos becomes “The till”, failed becomes “Failed”, not_on_till becomes “Not on the till”.
  4. Turn errors into what to do. Not otp_expired, but “This link has expired. Send a new one.” Log the raw error for the operator.
  5. Drop the citation. “Gift cards are sold in the shop only (plan 29)” loses nothing as “Gift cards are sold in the shop only”.

5. One place for labels

  • Each kind of value that reaches a screen has one label map in shared code (a contracts or domain library both the server and the screens can import), for example tillFieldLabel(field), STATUS_LABELS, ORIGIN_LABELS.
  • Screens, server messages, emails and exports all use the same map, so a value has the same name everywhere.
  • The map falls back to the raw value for an unknown key, so a new field shows up rather than breaking the page. A test lists every known key and checks it has a label, so the fallback is never what users see.
  • Server text that names a value (“Points per item sold had changed on the till first”) goes through the same map before it is sent.
  • A filter or select sends the raw key and shows the label: <option [value]="f">{{ label(f) }}</option>.

6. Technical details

Some screens exist to diagnose problems: a sync record, the raw row another system sent, an error as it was received. Those may show internal names, under three conditions:

  • Folded away under a heading in plain words, such as “Technical details” or “Till record”, closed by default.
  • Shown only to people with the permission for operating the app, not to everyone who can see the page.
  • The heading's one-line description says what it's for in plain words (“The records exactly as the till sent them, for diagnosing sync problems”), without the internal names themselves.

7. User documentation

  • The user guide uses the screen's words and describes what the reader sees and does. It never says “since plan n7”, “the till_deleted_at mark” or “the narrowToTill check”.
  • When a feature arrives, the user guide says what changed for the reader (“Products the till has deleted are now hidden from the products list”), not which plan built it.
  • Internal documentation links to the user guide for wording, and may cite plans, code and tables freely. A runbook written for an operator is internal; a help page in the app is not.
  • Release notes for users follow the user guide's rule. Release notes for the team may cite plans.

8. Building from a plan

  • Plans cite sections, decisions and other plans, and a build naturally copies those into what it writes. Keep them in code comments (“Plan 2026-11-23 n7 §3.5: …”) and out of strings.
  • A plan's wording for a screen is a proposal for the screen. Wording in the plan that explains the plan (“until plan n8 ships”) is not screen text.
  • When a subagent builds part of a plan, its brief says so: “No plan references, section numbers or code names in anything a user reads; label maps for values.”
  • The plan's verification includes the check in §10.

10. Checking an app

  1. Search the strings. In the screens' templates and the server's user-facing strings (messages, descriptions, warnings, email templates), search for plan references, skipping comments. For example: 
    grep -rnE "([Pp]lan (n?[0-9]|20[0-9]{2})|§[0-9]|\bT[0-9]{2,3}\b)" src --include=*.ts \
  | grep -vE "^\S+:[0-9]+:\s*(//|\*|/\*|<!--)"
    Then the same for the project's own internal names: its table names, its other systems' table and column names, and its field keys inside {{ }} bindings without a label function.
  2. Look at the bindings. Every {{ x.field }}, {{ x.status }} or {{ x.kind }} that shows a stored value goes through a label map.
  3. Read the new screens. Before a release, read each new or changed screen as someone who has never seen the code or the plans. Anything they wouldn't understand is either renamed or moved under Technical details.
  4. Test the labels. Specs assert the label on screen (“Points per item sold”), not the raw key, so a regression fails a test.
