Step naming guideline

1. Summary

  • Every step in a guide, runbook or procedure starts with a short name that says what the step does, such as Set GitHub secrets or Create the site folder. The details come after the name.
  • A name is a verb and the thing it acts on, in two to five plain words.
  • The name sits in bold at the start of the step, after the step number: 13. Set GitHub secrets. In the repository's Actions secrets, add…
  • Read in order, the names alone tell the story of the whole procedure.

2. Why name steps

A bare step tells the reader what to type or click, but not what it's for. A name gives each step a purpose the reader can hold on to.

  • Understanding. The reader knows what a step achieves before reading how, so the details make sense as they come.
  • Memory. "Set GitHub secrets, then put the files on the server" is easy to remember. A list of commands isn't. After a few runs, the names are the procedure.
  • Overview. Skimming the bold names gives the whole process at a glance, and shows how far along you are.
  • Talking about it. "Step 13, Set GitHub secrets" can be referred to and searched for. "Step 13" alone means nothing once steps are added or moved.
  • Fixing problems. When something fails, the name says which job didn't get done, which points at what to check.

3. How to write a step name

  1. Start with a verb. Use the command form: Set, Create, Copy, Point, Run, Check, Remove.
  2. Name the thing it acts on. Set GitHub secrets, not Set secrets, when there are several kinds of secret in the guide.
  3. Say what it achieves, not how. Make the secret files private, not Run chmod 600. Commands, paths and values belong in the details.
  4. Keep it short. Two to five words. If it needs more, the step is probably two steps.
  5. Use plain words. Use the words the reader would use. A file or setting name is fine when it's what the reader looks for, such as Fill in api.env.
  6. Make it unique. No two steps in one guide share a name. If two steps look alike, name what differs: Restart the API with the admin URL and Restart the API without it.
  7. Reuse verbs across guides. The same action gets the same verb everywhere, so Check always means "look, change nothing".

4. Where the name goes

  • In bold at the start of the step, after its visible number (HTML documentation guideline, §3), and ending with a full stop.
  • The details follow on the same line or in a nested list.
  • Sections are named the same way, by what they achieve: 3. Set up GitHub, 4. Put the files on the server.
  • For a long guide, an optional "At a glance" list near the top gives just the step names in order.

  <li><strong>Set GitHub secrets.</strong> In the repository's Actions secrets, add
    <code>VPS_IP</code>, <code>VPS_USER</code>, …</li>
  <li><strong>Put the workflows on master.</strong> The Run workflow button only
    appears once they are.</li>
</ol>

5. Examples

From a deploy guide:

Create the folder /opt/myapp on the VPS.Create the site folder. Create /opt/myapp on the VPS.
Make api.env and .deploy.env private (mode 600), and make deploy the owner.Lock down the secret files. Make api.env and .deploy.env private (mode 600), and make deploy the owner.
Set DATABASE_URL to the Supabase pooler address as app_user, with its password.Set the Supabase password in api.env. Set DATABASE_URL to the pooler address as app_user, with its password.

Remove DATABASE_ADMIN_URL from api.env and restart.Remove the admin password. Delete DATABASE_ADMIN_URL from api.env and restart.

Read alone, the names on the right tell the story: create the site folder, lock down the secret files, set the Supabase password, start the first release, remove the admin password.

6. Checking a guide

  1. Read only the names. In order, they should describe the whole procedure without the details.
  2. Match name and step. Each name says what its step does, and nothing the step doesn't do.
  3. Look for repeats. No two steps share a name.
  4. Look for commands. No name is just a command or a path.
