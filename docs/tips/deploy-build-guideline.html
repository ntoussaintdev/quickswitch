Deploy build guideline

How a repository builds the Docker image its deploys run: the same pinned packages as development, built the same way every time. Copy it into a project's docs/tips/ and follow it in the Dockerfile.

1. Summary

  • The image installs from the repository's own lock file (package-lock.json) with npm ci, never from a lock file a build tool generates.
  • The image uses the Node (or Python) version development uses, on Linux, with the dependencies installed inside the image.
  • The image name in the compose file is the one the workflow builds and pushes.

2. One lock file: the repository's

  • The rule. Every npm ci in the Dockerfile reads the repository's root package.json and package-lock.json, the files development installs from. The image then runs exactly the package versions that were tested.
  • Not a generated one. Some build tools write a trimmed package.json and package-lock.json next to their output (Nx with generatePackageJson: true, under dist/apps/<app>/). That lock file can miss packages, and npm ci then refuses to install ("not in sync … Missing: content-type@1.0.5 from lock file"). The option can stay on, but nothing installs from its output.
  • The cost. The image holds the runtime dependencies of every app in the repository, not only the one it runs: a few more megabytes, in exchange for one tested set of versions.
  • Commit the lock file. package-lock.json is in git and updated with every dependency change. npm ci fails when it doesn't match package.json, which is the point.

3. The Node image

Three stages: build with all dependencies, install the production dependencies from the same root files, then the runtime image with only what runs.

# 1. Build: all dependencies, from the repository's lock file.
FROM node:24-bookworm-slim AS build
WORKDIR /repo
ENV CI=true
COPY package.json package-lock.json ./
# With npm workspaces, also copy each workspace's package.json before npm ci (§3.1).
RUN npm ci --no-audit --no-fund
COPY . .
RUN npm run build

# 2. Production dependencies only, from the same root files.
FROM node:24-bookworm-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev --no-audit --no-fund && npm cache clean --force

# 3. Runtime: production dependencies and the build output.
FROM node:24-bookworm-slim
ENV NODE_ENV=production PORT=3000
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /repo/dist/ ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=30s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/api/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "main.js"]

3.1 Rules

  • Workspaces. With npm workspaces, stage 2 also needs each workspace's package.json. Simpler: drop stage 2, run npm prune --omit=dev --no-audit --no-fund at the end of stage 1 and copy its node_modules. Both install from the root lock file.
  • Runtime packages are dependencies. Anything the server imports at run time is in dependencies, not devDependencies, or the container fails at start with "Cannot find module".
  • Install scripts. A prepare script calling a dev tool (husky, for example) fails under --omit=dev. Make it tolerate the tool's absence, or add --ignore-scripts when no runtime package needs its install script.
  • A health route. The app answers /api/health (or its equivalent) on its port, so the HEALTHCHECK and the deploy can tell a running app from a crashed one.

4. Close to development

The same lock file gives the same package versions. The remaining differences between development and the image come from these, so keep them aligned:

WhatRule
Node versionThe image's major version is development's: node:24-… with "engines": { "node": ">=24 <25" } in package.json (or .nvmrc). Change both together.
Operating systemThe image is Linux, where file names are case-sensitive: an import of ./Header for header.ts works on Windows and fails in the image.
Native packagesInstalled inside the image, never copied from the PC. .dockerignore lists node_modules, dist and every .env* file.
Build modeThe image runs the production build, not the dev server. Run the production build in development too before a release.
SettingsCome from the environment file on the server (api.env), never baked into the image. .env.example lists every name.

5. Image name and tag

  • The compose file's image: is ghcr.io/<owner>/<name>:${IMAGE_TAG}, and the workflow builds and pushes exactly that name. When DevDock generates the workflow, the container's Image field in the environment holds the same name.
  • The tag is the full commit SHA, never latest, so a release is immutable and a rollback is a tag change.
  • Staging and live use the same image name, so a SHA built once can be deployed to both.

6. Python

  • Install from a pinned file: requirements.txt made with pip-compile (or uv.lock), exact versions, committed. Not a list of loose names.
  • The image's Python minor version is development's (python:3.12-slim with 3.12 locally).
  • Set PYTHONDONTWRITEBYTECODE=1, PYTHONUNBUFFERED=1 and PIP_NO_CACHE_DIR=1, and run as a non-root user.

7. Known failures

SeenCauseFix
npm ci: "not in sync … Missing: … from lock file"Installing from a generated lock file, or package-lock.json not updated after a dependency change.§2: install from the root files. Run npm install locally and commit the lock file.
Deploy: "failed to resolve reference … not found"The server pulls a different image name than the workflow pushed, or a SHA that was never built.§5: one name in the compose file, the workflow and DevDock's Image field.
Container exits: "Cannot find module"A runtime package in devDependencies, or a file name with the wrong case.§3.1, §4.
Install fails in a prepare scriptThe script calls a dev tool under --omit=dev.§3.1.

8. Adopting it in a repository

  1. Copy this file into the repository's docs/tips/.
  2. Check the Dockerfile against §2–§4, and the compose file and workflow against §5.
  3. Add a line to the repository's CLAUDE.md: "The Dockerfile follows docs/tips/deploy-build-guideline.html."
