Domain-driven design, the way we do it

Tip · written 2026-11-04 · for TypeScript monorepos built mostly by AI coding agents

1. Summary

  • We use DDD's strategic ideas fully: one shared vocabulary, bounded contexts, aggregates with clear owners, and a domain layer free of frameworks.
  • We use a functional style for the code: domain objects are plain readonly data, behaviour is pure functions, and there are no entity classes.
  • We derive whatever can be derived. We store facts and compute balances, matches and states from them.
  • Every rule has one home in the domain package. The client runs it for instant feedback, and the authoritative write side runs it again.
  • None of it depends on a build tool. Lint enforces the boundaries. For the monorepo, use Turborepo by default, or Nx when the repo is planned to grow large (§4.4).
  • The test of the design is whether an agent can work in one context without reading the others, and whether a forgotten rule fails loudly.

3. Ubiquitous language

  1. Keep a glossary of domain terms in the agent instructions (CLAUDE.md / AGENTS.md). Capitalize the terms and always use them precisely, so an agent sees the vocabulary in every session.
  2. Use one word per concept. Where the business has synonyms, write the mapping down ("Indicator = Process") and pick one word for the code.
  3. Write down where code names and UI words differ, for example "the UI says Trade, never OrderMatch".
  4. Treat a rename as a refactor. Change the glossary, the code and the UI copy in one change, and leave compatibility names only with a comment saying why.
  5. Retire terms explicitly. A retired concept gets a line saying it must not come back ("Workbench is retired: no code path may read or write it"). Otherwise agents that find the old names will bring the concept back.

4. Bounded contexts

4.1 Shape

  • A context is a part of the domain with its own words and rules, such as Trading, Learning or Presentation.
  • Each context is one folder in the domain package, or its own lib once it is big. It has an index.ts as its public surface, and other contexts import only that index.
  • The shared kernel (shared contract types plus a small kernel folder) holds only what two or more contexts need. Code tends to drift into it, so review what lands there.
  • Persistence and UI code stay in the apps, outside the contexts.

4.2 The context map

One section in the architecture doc names each context, what it owns and its folder, and says how the contexts relate:

Relationship Meaning Typical case
Shared kernel Types both sides own together; change them with care The contracts lib
Customer / supplier One context uses another's public surface Learning reads Trading facts
Conformist We copy an outside model exactly A faithful port, pinned by golden tests
Anti-corruption layer We translate an outside model into ours at one boundary An importer, an API client

4.3 Enforcement

  1. Between packages, a rule says which kinds of package may depend on which (apps → domain → contracts), and bans framework imports from the domain and contracts packages. The rule can come from the monorepo tool (§4.4) or a lint plugin; either way it runs in lint.
  2. Between folders in one package, use ESLint's no-restricted-imports: one files block per context folder, banning imports from the folders it may not use and deep imports past another context's index. This needs no monorepo tool at all.
  3. A package's package.json exports field makes its public surface hard to bypass: anything not exported can't be imported from outside.
  4. Run eslint in the pre-commit hook so a crossed boundary blocks the commit. Agents break rules that exist only in the docs.
  5. When adding a boundary to existing code, measure the crossings first. Fix them, or list them as named exceptions, so the rule passes from the start.

4.4 Choosing a monorepo tool

DDD doesn't need any particular build tool. A monorepo tool runs tasks in dependency order, caches their results and runs only what changed. The design in this guide works the same with either choice below.

  1. Default: Turborepo. Use it for most new projects. It is a thin layer over package-manager workspaces (a package.json per package and one turbo.json) that runs your own scripts, so it is quick to set up and easy to leave. For boundaries, use eslint-plugin-boundaries or no-restricted-imports (§4.3). Treat Turborepo's own boundaries check as an extra until it is stable.
  2. Nx, when the repo is planned to grow large. Choose it from the start if you expect many apps and libraries, a framework with heavy upgrades (Angular, NestJS), several languages, or long CI runs. It adds a mature boundary rule with tags (@nx/enforce-module-boundaries), generators, automated upgrades (nx migrate), language plugins and CI runs spread across machines.
  3. Don't switch for speed. The two run at similar speeds; what decides speed is the cache hit rate, correct inputs/outputs, running only what changed, and a shared remote cache. Move from Turborepo to Nx when the repo's size or upgrade work calls for it, not before.
  4. Mostly another language, or several in equal measure: use a tool built for it (moon, Pants, Gradle, Bazel) and that language's own boundary checks (ArchUnit, import-linter, Go internal/ packages).

5. Aggregates and ownership

  1. Every piece of durable data has exactly one owner, its aggregate. Write a table with "owns" and "must not own" columns in the architecture doc. The "must not own" column does as much work as the other one.
  2. Refer to another aggregate by id, never by embedding it. Use an id that stays the same for the thing's whole life: an id that changes when the thing changes state is the wrong reference.
  3. Give each aggregate a revision number for optimistic concurrency. A write names the revision it read, and the server refuses a stale one. Use separate revisions where parts change at different rates (content vs configuration).
  4. One write changes one aggregate. Where a gesture spans several (a copy, a transfer with two sides), run it in one server transaction inside a named service.
  5. Published things are immutable versions. There is a mutable draft, an immutable Version, and per-user state pinned to one Version. Nothing edits a Version after it is published.
  6. Runtime state is not an aggregate. Open windows, timers, queues and the current cursor live in a runtime layer and are never persisted as they are.

6. Values and derived state

  • A value object is a readonly type with no identity: a reference, a meaning, a time range, a rule snapshot. Compare it by content.
  • Store facts and derive everything else. Orders and cash entries are facts. Trades, balances, drawdown and rule state are computed by pure functions that replay the facts. Derived values are never stored, so they can never be stale.
  • When deriving is too slow, cache the result keyed on the facts' revision. Never keep it as a second source of truth.
  • A snapshot is a fact too. When a rule set is copied into a record ("the rules this attempt started under"), store the copy plus the id and version it came from.

7. Where rules live

7.1 The rule

  1. Every invariant is a pure function in the domain package, in its context's folder.
  2. The client calls it before writing, for an instant, friendly refusal.
  3. The authoritative write side calls the same function and refuses the write if it fails. The server is the one side that can't be bypassed.
  4. Specs test the function once, and each side has a thin spec showing that it calls it.

7.2 Hooks per type

With a generic data model (typed records in collections), put the rules on a registry entry per type rather than in the handlers: 

interface TypeDefinition<T> {
  validate(next: T): boolean;                      // shape and values
  validateChange?(prev: T | null, next: T | null,
                  ctx: WriteContext): string | null; // transitions: locks, pairs, values that only grow
}
  • validate checks one record on its own. validateChange checks a transition: a locked record being edited, a value that may only grow being made smaller, one half of a pair being removed.
  • The write context is loaded once per command, never once per record.
  • Refusals are in plain words, so the client can show them as they are.

7.3 Choke points

Some rules need runtime state the server doesn't have, such as the live price or the current cursor. Each such rule gets one choke-point function on the client that every path goes through, with a comment there. Treat it as debt: a plan to make the server check it should exist, even if it's deferred.

8. Commands and events

  • Writes are typed commands, not raw CRUD. A command names its aggregate and the revision it expects, and returns the new revisions.
  • Generic commands (save these records, append to this list) suit editing data. With them, the rules belong in the per-type hooks (§7.2).
  • Domain commands (order.place) suit actions whose rules span several records, and they make it obvious who owns the rule. Add one when the hooks get awkward, not by default.
  • An event is a fact record ("order submitted"), stored or emitted after a write succeeds. Other contexts read the facts and never reach into the writer's internals.
  • Optimistic client updates revert when the server refuses them. Async check-then-create work is serialized per resource key.

9. Ports and adapters

  1. The domain package imports no framework, ORM, UI library or chart library, and lint bans them.
  2. Repositories are ports in their own lib, with adapters (in-memory for tests, local storage, HTTP). Domain code never knows which one it has.
  3. Each third-party library sits behind one adapter file. The data it stores is plain JSON that the rest of the code treats as opaque. Heavy libraries load lazily.
  4. Serialization to storage happens at exactly one boundary (one serializers file), so storage quirks never leak inward.
  5. An outside model enters through an anti-corruption layer (an importer). The importer keys records by the source's own id and hash, so a re-import can tell local edits from changes at the source.

10. Why it suits agents

Practice What an agent gains
Glossary in the instructions Consistent names in code and copy, without being told each time
Context folders with an index It reads one context, not the whole lib, and makes fewer edits in the wrong place
Lint-enforced boundaries A wrong import fails at commit, not at review
Rules run by the write side A forgotten call becomes a refused write and a failing spec
Pure domain functions Cheap, fast specs with no framework setup, so it can check its own work
Derived instead of stored state No "remember to update X too" code paths
A CLAUDE.md / AGENTS.md per context A context's gotchas load only when it works there, and the root file stays short
Context map It knows where a feature belongs before it starts searching
Contexts as lanes Parallel agents touch separate folders and conflict less

11. Warning signs

  • "A new path must call X" lines piling up in CLAUDE.md. The rule is in the wrong place. Move it to the domain and the write side, then delete the line.
  • A facade class thousands of lines long. A thin entry point is fine, but domain logic inside it is invisible to the server and hard for an agent to take in. Move the pure parts into the domain package.
  • The shared contracts lib as a dumping ground. A type used by one context belongs in that context.
  • Stored totals, counts or statuses that could be derived. They drift. Derive them, or cache them keyed on a revision.
  • Deep imports into another context's files. Use its index, or move the thing into the kernel.
  • Filename prefixes standing in for folders (lab-*, order-*). These are contexts that haven't been named yet.

12. Checklist

12.1 A new project

  1. Write the glossary into CLAUDE.md / AGENTS.md before the first feature.
  2. Pick the monorepo tool (§4.4): Turborepo by default, Nx if the repo is planned to grow large.
  3. Create contracts, domain and persistence packages. Put the package dependency rule and the framework bans in the root eslint config.
  4. Add a pre-commit hook that runs eslint on staged files.
  5. Write the ownership table and the context map in the architecture doc.
  6. Create one folder per context, with an index.ts and a short CLAUDE.md / AGENTS.md.
  7. Make the write side call the per-type validate hooks from day one.

12.2 A new feature

  1. Name its context. If none fits, decide whether it is a new context and add it to the map.
  2. Add any new terms to the glossary.
  3. Name the aggregate that owns its data, and what that aggregate must not own.
  4. Decide what is stored (facts) and what is derived.
  5. Write each rule as a pure function in the context, call it on both sides, and spec it.
  6. Put the feature's gotchas in that context's CLAUDE.md, and only the ones no check can catch.
