Technical plan · Windows 11 · Rust · egui 0.37 / eframe 0.37 · v1

QuickSwitch: a Spotlight-style Rust launcher with egui

Build a small native Windows tool that opens with Ctrl + Win + K, searches open window titles and individual File Explorer tabs, and launches folders from Linux-friendly path input. The process keeps running in the system tray until explicitly exited, with an optional “Start with Windows” setting.

egui + eframeOne executableTray residentNo ElectronStartup opt-in

1. Summary

Recommended implementation: one Rust GUI process using eframe + egui for the borderless search popup; tray-icon for the notification area; global-hotkey for the shortcut; and the windows crate for window switching and COM/UI Automation. Run UI Automation on a dedicated MTA worker thread. Use a small fuzzy matcher to filter a snapshot of open windows and Explorer tabs.

Scope of v1: launch silently into the notification area; show a centered search box; select a matching open window or Explorer tab; accept ~/folder, C:/folder and UNC folder paths; expose a tray-menu option to enable or disable per-user startup.

Critical uncertainty: there is no promised stable, Explorer-tab-specific control API in this plan. Individual tab activation depends on what File Explorer exposes through UI Automation on the installed Windows build. Validate this with a small spike before implementing the entire UI.

Not in v1: disk-wide search, search inside Chrome/Edge tabs, WSL/Linux filesystem translation, indexing, a plugin framework, auto-updating, cloud services or elevated privileges.

2.2 Visual and keyboard details

  • Show a borderless, focusable popup approximately 680 × 340 logical pixels, scaling for display DPI. Center it over the active foreground window’s monitor, not always the primary monitor.
  • One egui::TextEdit search input and up to 8–10 results. Each result shows a title and a small kind label: Window, Explorer tab, or Open folder.
  • Support duplicate names by including application or Explorer-window context. Remember the most recently selected results to improve ordering.
  • Windows that are minimized should be restored before activation. Failed switches must show a short error instead of silently closing.

3.2 eframe API detail that matters

In eframe 0.37, the application implements App::ui(&mut self, ui, frame) for rendering and may implement App::logic(&mut self, ctx, frame) for non-rendering work. The logic hook can run on repaint requests even when the window is hidden. This is a better fit than relying on the older App::update examples you may find online.

// Minimal illustration of a hidden root viewport; not the full tray integration.
let native_options = eframe::NativeOptions {
    viewport: eframe::egui::ViewportBuilder::default()
        .with_title("QuickSwitch")
        .with_inner_size([680.0, 340.0])
        .with_decorations(false)
        .with_resizable(false)
        .with_taskbar(false)
        .with_visible(false),
    ..Default::default()
};
eframe::run_native(
    "QuickSwitch",
    native_options,
    Box::new(|cc| Ok(Box::new(QuickSwitchApp::new(cc)))),
)?;

The root viewport is hidden, not closed. In logic, drain queued commands such as Open/Hide, send ViewportCommand::Visible(bool) and ViewportCommand::Focus, and request paint only for state changes. On the popup render pass, use egui::TextEdit::singleline, capture arrow/Enter/Escape, and request focus for the input when shown. Never send ViewportCommand::Close just to dismiss the palette: closing the root typically exits the program. Test the exact wake-up and focus behavior on Windows.

4. Runtime architecture

One native event loop, one hidden root viewport, one UI Automation worker. Let eframe/winit own the Windows event loop. Create the tray icon and hotkey manager on that event-loop thread (during app initialization, after the loop exists). Relay hotkey, tray and menu events into a non-blocking app-command queue, then call egui::Context::request_repaint to wake the hidden app. Keep UIA COM objects on their dedicated MTA thread and transmit only owned result metadata.

4.2 Runtime ownership and window lifecycle

OwnerResponsibilitiesDoes not do
Main thread: eframe + eguiNative event pump, popup state, tray/hotkey handles, command dispatch, search UITraverse Explorer UIA providers synchronously
UIA worker (MTA)Enumerate TabItem elements, maintain short-lived tab handles, select requested tabTouch egui state directly or paint widgets
Search modelPlain cloned result records, filtering, ranking, path parsingKeep COM interface objects or native window handles beyond validation

Do not rely on receiving UI callbacks just because a channel has data. Use each crate’s documented event-handler hook (or a dedicated bridge) to enqueue a command and call request_repaint. eframe::App::logic is allowed to handle commands while hidden, but must not render UI. On an Open command, restore visibility and arrange focus; on Hide, set Visible(false). Only an explicit Exit should shut down the root viewport.

4.4 Initialization and shutdown pseudocode

MAIN:
  acquire per-user singleton lock (or signal existing QuickSwitch, exit)
  create eframe root viewport with visible=false, taskbar=false
  on eframe event-loop thread: create tray-icon + global-hotkey
  initialize App with command queue and egui context
  start UIA worker (MTA)
  event handlers: enqueue command; ctx.request_repaint()
  App::logic: drain commands; show/hide viewport; collect worker results
  App::ui: render TextEdit, ranked results and status only when visible
  tray Exit: unregister shortcut; drop tray icon; stop worker; exit root
  OS session shutdown: best-effort cleanup

5. Search & action model

5.1 Result types

enum Target {
    Window { hwnd: isize },
    ExplorerTab { explorer_hwnd: isize, token: u64 },
    OpenFolder { path: std::path::PathBuf },
}

struct SearchItem {
    title: String,
    subtitle: String,
    target: Target,
    recent_rank: Option,
}

This is a planning sketch, not ready-to-compile source. Explorer-tab token is an ephemeral identifier owned by the worker. Do not pass raw COM pointers between threads or assume UIA runtime identifiers remain valid after Explorer changes.

5.2 Search semantics

  1. Free text: match window title and Explorer tab names; rank prefix and contiguous matches first, then fuzzy matches, then recent picks.
  2. Clearly path-like input: produce an Open folder action when input begins with ~/, ./, a drive prefix such as C:/, or a UNC prefix such as //server/share. Do not interpret bare words as paths by default.
  3. Path conversions: ~/docs → %USERPROFILE%\docs; normalize separators; allow spaces; confirm the resolved target is a directory.
  4. Relative paths: for v1, resolve ./folder relative to the user’s home directory, and document that choice. Avoid relying on the executable’s current working directory.
  5. Out of scope: ~otheruser, WSL paths such as /home/alice, and shell expression expansion are not silently translated. //server/share is a Windows UNC path, not a WSL path.

5.3 Freshness strategy

On popup open, collect top-level window titles synchronously (usually cheap), show those results immediately, and request Explorer tabs from the UIA worker. Merge tab results on arrival. Type-to-filter works entirely on the current snapshot. When a selected target has disappeared, refresh rather than crashing.

The worker should limit its search to known Explorer windows and the corresponding tab strip—not every accessibility descendant of every app. Debounce repeated refresh requests and avoid blocking the UI if one Explorer instance hangs.

6. Implementation steps

6.1 Phase 0 — De-risk Explorer tabs (first)

Step 1. Create a UIA diagnostic command-line binary

Before the GUI, write a small Rust spike that initializes COM MTA, enumerates Explorer windows (e.g. CabinetWClass candidates), discovers relevant TabItem names in each window’s accessibility tree, and logs control patterns and tab labels.

Step 2. Prove inactive-tab selection

Test at least two Explorer windows with three tabs each. Attempt SelectionItemPattern::Select on an inactive tab, then foreground its Explorer window. Check duplicate labels and provider changes after moving/closing tabs.

Gate M0: either inactive tabs can be selected on your Windows 11 build, or a window-only fallback is explicitly accepted.

6.2 Phase 1 — eframe shell, tray and hotkey

Step 3. Scaffold eframe + egui

cargo new quickswitch --bin
cd quickswitch
# Add the dependencies from §3.1
cargo check
cargo run

Target x86_64-pc-windows-msvc. Begin with a visible egui::CentralPanel to confirm input and fonts; then change to a hidden root viewport using ViewportBuilder::with_visible(false). Add #![windows_subsystem = "windows"] only after console-based diagnostics are no longer needed.

Step 4. Create the native tray icon

Build a tray-icon icon and menu on the thread that runs the native event loop. Menu: Open Search, checkable Start with Windows, Exit. Retain the tray handle for the whole process. Clicking the icon opens search.

Step 5. Register Ctrl + Win + K

Use global-hotkey on the event-loop thread, handle registration failure without crashing, and detect keypress events. Register a fallback shortcut only when configured; never silently steal a different shortcut. A tray notice/log should explain conflicts.

Step 6. Wire the hidden-window wake-up

Make hotkey and tray callbacks enqueue a command and call egui::Context::request_repaint. In App::logic, process Open/Hide/Exit. Show with ViewportCommand::Visible(true); hide with Visible(false). Verify a hidden window wakes from a hotkey without a repeating timer.

Gate M1: process starts with no visible window, responds to hotkey/tray, survives repeated open/hide cycles, and quits only from Exit.

6.3 Phase 2 — Polished search and window switching

Step 7. Implement the egui palette

Make a ~680 × 340 logical-pixel, undecorated popup with egui::TextEdit::singleline, a scrollable results list, focus/keyboard controls and status/footer. Implement the interaction from §2.3. On Open, clear stale query if desired, update results, center over the current active monitor, show and focus text input. On Escape/focus loss, hide only.

Step 8. Enumerate and filter visible windows

Use Win32 EnumWindows, IsWindowVisible, GetWindowTextW, ownership/style checks, and optional DWM cloaking filters. Exclude QuickSwitch, untitled helper/tool windows and non-switchable surfaces. Use nucleo-matcher to filter the in-memory snapshot on keystrokes.

Step 9. Switch and restore Windows windows

On Enter: verify the target HWND still exists, restore if minimized, then attempt SetForegroundWindow. Respect Windows foreground restrictions, and show a short error if activation fails. Never keep an invalid HWND as a permanent identity.

Gate M2: search title bars in at least ten applications and switch to the correct normal or minimized window; popup closes but tray remains.

6.4 Phase 3 — Explorer tabs and Linux-style paths

Step 10. Connect the UI Automation worker

Keep COM UIA on a dedicated long-lived MTA worker. On opening the palette, send Explorer window candidates; return plain SearchItem records asynchronously. Refresh tab targets before invoking them and select via the worker. Do not traverse arbitrary app accessibility trees or block the eframe thread.

Step 11. Build the path resolver

Accept ~/projects, C:/dev/work, ./notes, and //server/share as path-like input. Expand ~ to the current Windows home folder, normalize slash separators without breaking UNC prefixes, and resolve ./ relative to the chosen documented home base. Validate directories before launching.

Step 12. Open Explorer and test the new-window contract

Use argument-safe process invocation, not shell string concatenation. On Windows 11, opening a directory can reuse an existing Explorer window or create a tab depending on user settings and shell behavior. Test that new window actually means a second top-level Explorer window, and do not assume a legacy /n switch guarantees it.

Gate M3: your sample tabs search individually; a tab target selects the right Explorer instance; Linux-style path inputs open the correct folder with verified window behavior.

6.5 Phase 4 — Autostart, singleton and lifecycle

Step 13. Implement checkable Start with Windows

Read the real app-owned value from HKCU\Software\Microsoft\Windows\CurrentVersion\Run. When enabled, write an absolute quoted path to the installed exe, optionally with --background. When disabled, delete only the QuickSwitch value. Make login startup off by default; keep the value on normal Exit.

Step 14. Add single-instance and second-launch behavior

Use a per-user named mutex plus a simple native IPC wake-up (named pipe or registered message with verified sender) so invoking the executable again opens the running instance instead of creating a second tray icon. Test sign-in races and no-elevation installs.

Step 15. Implement robust shutdown

Explicitly Exit only from the tray or Windows session ending. Unregister the hotkey, drop the tray/menu handles, stop the UIA worker and COM apartment, save settings, then close the root viewport. Handle unexpected Explorer/taskbar restart by verifying the tray icon can recover.

Gate M4: user can hide the popup 100 times, open it again, toggle startup, and exit without ghost processes or duplicate icons.

6.6 Phase 5 — Tests, performance, packaging

Step 16. Profile idle vs visible resources

Compare glow against default wgpu; measure startup latency, idle working set/commit, visible memory, CPU idle, and shortcut-to-paint response. Aim for near-zero CPU when idle, not zero RAM. No redraw loop while hidden; do not call request_repaint_after repeatedly unless necessary.

Step 17. Build an installed release

Run cargo fmt --check, cargo clippy --all-targets -- -D warnings, cargo test, then cargo build --release. Embed an app icon, install under %LOCALAPPDATA%\Programs\QuickSwitch, and verify Start with Windows after a real sign-out/sign-in. Ship ZIP initially; add installer/signing when distributing.

Gate M5: a new user can install, run, switch, open a folder, enable or disable startup, and exit with no admin permissions.

7. Tray, startup & lifecycle

7.1 Tray menu specification

QuickSwitch
────────────────────
Open search                 Ctrl + Win + K
☐ Start with Windows
────────────────────
Exit

Left-click the tray icon to open search; right-click to display the menu. The checkbox state reflects the actual registry value, not merely the last clicked value. If startup registration fails, leave the checkbox unchanged and display an error.

7.2 Startup implementation

Store a single string value named QuickSwitch under HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run. Example value data:

"C:\Users\<user>\AppData\Local\Programs\QuickSwitch\QuickSwitch.exe" --background

Important: “Start with Windows” means launch after the user logs in, not before login as a Windows service. It defaults to off. Point the entry at a stable installed location, not target\debug\quickswitch.exe, which may move or be deleted.

9. Tests & acceptance

9.1 Automated tests

  • T1 — Path parsing: ~/src, C:/src/app, //server/share, ./notes, spaces, missing directories and malformed paths.
  • T2 — Ranking: case-insensitive matching, fuzzy typos, empty query, duplicate titles, prefix priority and recency ranking.
  • T3 — Settings: defaults, save/load round-trip, invalid config fallback and startup path quoting.
  • T4 — Result lifecycle: stale HWND, tab disappears while the palette is open, late worker response after palette closes.

10. Packaging & release

10.1 Release workflow

  1. Step 1. Build and test on Windows: cargo fmt --check, cargo clippy --all-targets -- -D warnings, cargo test.
  2. Step 2. Create the optimized executable: cargo build --release.
  3. Step 3. Embed a real tray icon, matching egui app icon and version metadata; sign the binary if distributing publicly.
  4. Step 4. Ship a ZIP or tiny per-user installer to put QuickSwitch.exe at a stable path under %LOCALAPPDATA%\Programs\QuickSwitch.
  5. Step 5. Do not enable startup during installation without the user's choice. If uninstalling, remove the app-owned Run entry and files.
